# 决策草稿 0008：P0.1 数据库与 Mac 媒体职责

执行说明：用户已批准启动P0.1；本文审核稿作为执行基线，R0审核收敛后冻结。历史“未启动”描述不再代表现行状态；进度见state.json。


版本：0.1.0｜日期：2026-10-13｜状态：建议采用，待用户审核；未生效

用户要求 P0.1 围绕 SQL 与 Mac 存储两部分推进，先形成计划审核，不开始开发。本文明确推荐选择，不用多个备选作为执行默认。

| 问题 | 推荐决定 | 理由及代价 |
| --- | --- | --- |
| 业务数据库 | PostgreSQL 17 | 适合后续事务与并发扩展；新增一个持久化服务与恢复责任 |
| Go 访问方式 | `database/sql` + pgx v5 stdlib，显式 SQL | 沿用现有边界，避免同时引入 ORM 重构；必须改 SQL 方言和事务语义 |
| 结构迁移 | goose v3，独立迁移命令 | 版本化 SQL 和明确发布动作，业务启动不自动改表 |
| Redis | 不采用 | 当前单使用者、有界队列和元数据规模没有需要它的已验证问题 |
| SQLite 保留方式 | 只读导入工具与旧发布备份 | 避免长期双引擎兼容；新写入后不能无损直接退回旧 SQLite |
| Mac 职责 | 媒体主存储、FFmpeg、ZIP；Go 媒体 Agent | 视频/帧/ZIP 不必先复制到云端；Mac 在线成为媒体操作依赖 |
| 云端职责 | Go 业务 API、PostgreSQL、页面、监控；媒体流式转发 | 标注状态和任务管理仍由 Go 唯一负责 |
| 连接 | Mac 主动建立受限 SSH 反向隧道 | 不开放 Mac 入站端口；额外处理睡眠、断线和重连 |
| Mac 部署 | 同仓库 backend 独立入口，原生 Go + FFmpeg + launchd | 保持三模块；无需为 Mac 常驻服务强加 Docker Desktop |
| 旧云端媒体 | 兼容保留，不自动搬迁/删除 | 降低迁移风险；不宣称历史云端数据已全部离开磁盘 |
| 混合提供方导出 | 明确拒绝，按提供方分开导出 | 保持可验收范围，避免云端混合 ZIP 暂存破坏新媒体边界 |
| 公司真实 API | 本波次不作为门槛 | 本波次验证已授权本地媒体；真实内网 API 兼容不能用合成数据替代 |

没有采用 MySQL，因为此轮目标不是比较两个 SQL 引擎，也没有现成 MySQL 环境带来的必要约束；选择 PostgreSQL 后不继续铺双套方案。没有采用“云端下载 Mac 视频再用 FFmpeg”，因为它会复制媒体到云端。没有采用全媒体驻内存，因为 2核4GB 不适合承接完整视频/ZIP。

这份草稿不改写已冻结的 P0 规格和历史验收。用户批准后，Leader 记录确认事件和规格提交 SHA，更新状态；API/schema 的新增行为只在 P0.1 范围生效。
